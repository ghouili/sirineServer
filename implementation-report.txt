SlotyCare Backend Report (Steps 1-12)
====================================

Architecture Overview
- Stack: Node.js + Express + TypeScript + Prisma (MySQL)
- Multi-tenancy: shared DB + shared schema; tenant-scoped tables always filtered by tenant_id
- Auth: JWT with role claims; tenant routes require active subscription
- Validation: Zod; consistent JSON response shape

Environment Variables
- DATABASE_URL
- JWT_SECRET
- JWT_EXPIRES_IN
- PORT
- CORS_ORIGIN
- Gmail OAuth2 variables present for later steps

Models (Prisma Schema)
Global / Commercial
- super_admins: id, nom, email (unique), password_hash, created_at
- tenants: id, nom, slug (unique), logo_url?, status, created_at, updated_at
- licenses: id, nom, type, billing_period, duration_months, description?, prix_mensuel, features, is_active, created_at
- promotions: id, license_id, discount_rate, is_active, starts_at?, ends_at?, created_at
- subscriptions: id, tenant_id, license_id, status, billing_period, start_date, end_date,

Tenant-scoped

- patients: id, tenant_id, nom, prenom, telephone?, tags?, notes_internes?, created_at

- breaks: id, tenant_id, praticien_id, weekday, start_time, end_time
- time_off: id, tenant_id, praticien_id, start_at, end_at, reason?
- holidays: id, tenant_id, date, label?
- appointments: id, tenant_id, patient_id, praticien_id, service_id, date_heure_debut, date_heure_fin,
  status, no_show_probability_score?, ia_recommandation?
- waitlist_entries: id, tenant_id, service_id, praticien_id?, patient_name, patient_phone?, patient_email?,
  preferred_from?, preferred_to?, status, created_at
- notifications: id, tenant_id, appointment_id?, type, channel, to_email, subject, payload, schedule_at?,
  status, tries, sent_at?
- documents: id, tenant_id, patient_id, file_path, type_document, visibility_level, uploaded_by, created_at
- document_access_logs: id, tenant_id, document_id, user_id?, patient_id?, action, ip_address?, created_at
- audit_logs: id, tenant_id, user_id, action, details?, ip_address?, created_at

Key Methods / Services
- Tenant resolution: X-Tenant-Slug -> req.tenant; blocks missing/unknown/suspended tenants
- Subscription gating: requires active subscription (status=active and now between start/end)
- Auth: JWT-based; roles: super_admin, admin, praticien, assistant
- Availability engine: working hours - breaks - time off - holidays - overlapping appointments
- Appointment create: transaction + overlap check + tenant scoping
- Waitlist: open entry on create; when appointment canceled -> queued notification + status=notified
- Documents: upload to /uploads/{tenant_slug}/{patient_id}; view/download logs access

What to Do Later: Separate Databases Per Tenant
------------------------------------------------------------
Goal
- Move from shared DB/shared schema to separate databases per tenant for stronger isolation.

High-Level Steps
1) Introduce a tenant database registry
   - Add a global table (in the control DB) with tenant_id, db_name, db_host, db_user, db_password, db_status.
   - This becomes the source of truth for tenant DB connection details.

2) Update tenant resolver to attach DB credentials
   - After resolving tenant by slug, fetch its DB config.
   - Attach req.tenant.db or build a tenant-specific Prisma client.

3) Implement dynamic Prisma client creation
   - Create a Prisma client per tenant DB URL (cache per tenant for reuse).
   - Ensure correct pooling and cleanup on deploy or tenant removal.

4) Split migrations
   - Keep global tables (super_admins, licenses, promotions, tenants, subscriptions) in the control DB.
   - Run tenant schema migrations against each tenant database (users, appointments, etc.).

5) Update services to use tenant-specific client
   - Replace shared prisma instance with tenant-bound client for tenant-scoped tables.
   - Keep global queries on the control DB client.

6) Update seed and provisioning
   - Seed global DB with licenses/promotions.
   - For each tenant, provision a new DB + run migrations + seed tenant data.

7) Update monitoring and backups
   - Add tenant-level DB health checks.
   - Automate backups per tenant DB.

Why Shared DB is Better in Dev 
- Faster setup: one DB, one migration pipeline, fewer credentials.
- Lower cognitive load: devs focus on features instead of provisioning.
- Easier local testing: no need to spin up multiple tenant databases.
- Simplified CI: single DB instance for integration tests.
- Lower resource usage: fewer connections and less storage during development.

Note: once product maturity and compliance requirements increase, per-tenant DBs provide better isolation and easier data residency controls, but at the cost of operational complexity.
